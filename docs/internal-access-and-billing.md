# Доступ сотрудников и будущая подписка

Состояние на 15 октября 2026 года: бюджетный backend, миграции и клиент 1.0.1 выпущены. Добавлены Qwen3, cache-aware billing и журнал USD по чату. [Актуальная реализация и границы проверки](qwen3-cache-and-usage.md). Интеграционные billing-тесты используют отдельную PostgreSQL и подменённый inference; отдельные AWS audit вызовы подтвердили tools/vision/cache, но не заменяют платный production-запрос через приложение.

## Что было в коде

`User.tokenBalance` выдаёт 100 000 токенов при регистрации. Bedrock и платный OpenRouter списывали одинаковую сумму input + output без учёта разных цен. Платный OpenRouter дополнительно требовал `PRO`; бесплатные модели имели отдельные 150 запросов в сутки UTC. Админка могла добавить токены, блокировать аккаунт, выбрать провайдера и разрешить модели Bedrock.

Не было денежного баланса, истории начислений, ограничения на 5 часов/неделю, резервирования перед запросом или подписки. Прежний SSE-парсер терял usage при разделении JSON по сетевым пакетам. `/api/models` и клиент показывали бесплатный OpenRouter даже при фактическом использовании Bedrock. Прямого общего OpenAI backend-провайдера и интеграции рублёвых платежей в этих двух репозиториях не найдено. OpenAI-модели можно использовать через OpenRouter.

## Модель первого этапа

Сотрудник входит через существующий Яндекс/VK. Администратор находит его в `/admin/users`, открывает карточку, выбирает Bedrock/OpenRouter и выдаёт доступ за счёт компании. Отдельного типа «сотрудник» не требуется: это такой же пользователь с выданным бюджетом. Автоматической выдачи $20 всем зарегистрировавшимся нет.

| Параметр | Стартовое значение |
| --- | --- |
| Разовое начисление на тест | $20 бюджета API |
| Срок доступа от начисления | 30 дней |
| Денежный лимит за 5 часов | $2 |
| Денежный лимит за 7 дней | $5 |
| Запросов за 5 часов | 150 |
| Запросов за 7 дней | 1000 |
| Одновременных запросов одного аккаунта | 1 |
| Максимальный ответ | 4096 токенов |

$20 и окна с первого запроса выбраны пользователем. Остальные значения — изменяемые стартовые настройки внутреннего теста, не копия численных лимитов Codex/Claude. Один запрос означает один вызов модели, в том числе шаг инструмента агента, а не одно сообщение человека. Общий бюджет $20 действует на весь срок; сброс короткого окна не начисляет деньги. Окна независимы и общие для всех моделей. После истечения окна новое начинается с ближайшего разрешённого запроса. После 30 дней доступ по выданному бюджету закрывается, автоматически не продлевается.

Бесплатный OpenRouter расходует запросы, но не денежный бюджет. Bedrock расходует бюджет по каталожной стоимости до применения AWS credits. Кредиты провайдера — отдельная субсидия компании: их реальный остаток и итоговый счёт нужно сверять с AWS/OpenRouter. Они не меняют выданные сотруднику ограничения. $20 бюджета API не является будущей розничной ценой подписки.

Начисление с положительной суммой добавляет бюджет к остатку и задаёт срок от текущего момента. Настройка с суммой 0 меняет ограничения/паузу без продления срока. Окна при изменении настроек не обнуляются. Срок относится к аккаунту целиком; отдельных сроков сгорания у каждого начисления пока нет. Для месячной подписки понадобится отдельная политика переноса остатка, а не повторение ручного начисления.

Старый токеновый баланс не конвертируется в USD. Наличие `AccountBudget` переключает аккаунт на новый учёт, даже если доступ истёк или выключен. Для остальных пользователей временно сохраняется прежняя схема. Поэтому всех участников внутреннего теста, включая администратора как пользователя, нужно явно перевести через выдачу бюджета.

## Учёт и ограничения

Баланс хранится целым числом микродолларов: 1 USD = 1 000 000 единиц. Входные и выходные токены записываются отдельно. OpenRouter использует возвращённый `usage.cost`; Bedrock — usage токенов и цену из каталога, сохранённую в резерве. Смена цены после запроса не меняет его расчёт. При отсутствии цены платная модель недоступна. Для OpenRouter также задаётся `provider.max_price`, чтобы ограничить цену маршрута.

Перед отправкой сервер блокирует строку бюджета в PostgreSQL, проверяет бан, срок, остаток, оба окна и активный резерв. Затем списывает оценочный резерв и занимает запрос в обоих окнах. Резерв учитывает объём текста в UTF-8, служебный запас и максимальный ответ; это консервативная оценка, а не точный подсчёт токенов провайдера. Поэтому возле лимита сервер может попросить уменьшить контекст ещё до достижения фактического расхода. Изображения и платные серверные инструменты пока закрыты; текстовые блоки и локальные инструменты агента поддерживаются. Клиентские `n`, plugins и произвольные настройки провайдера не передаются.

После ответа сервер атомарно сохраняет usage и возвращает разницу между резервом и стоимостью. Повторное закрытие того же резерва ничего не списывает. `BudgetEntry` сохраняет начисление, резерв, возврат или корректировку; каждое имеет уникальный ключ. Повтор HTTP-запроса с тем же ключом и тем же содержимым не начисляет деньги дважды. Изменённое содержимое с прежним ключом отклоняется.

SSE читается с буфером между пакетами. После отмены клиентом сервер продолжает читать usage в пределах времени жизни запроса. Если usage не пришёл или ответ/сеть оборвались неопределённо, резерв остаётся списанным как `estimated`; это не подтверждённая стоимость. При явном отказе 4xx, кроме таймаута 408, резерв и запрос возвращаются. Неопределённые 5xx учитываются по оценке. Если сервер погиб или БД не приняла закрытие, запись остаётся `pending` и новые запросы блокируются. После 10 минут администратор может закрыть её по оценке: без возврата всей суммы. Это консервативный способ восстановить доступ, не оправдание выдавать неизвестное потребление бесплатно.

Если фактическая стоимость превысила оценку, реальный расход записывается полностью; баланс может стать отрицательным, а последующие платные запросы блокируются. Абсолютный предел счёта провайдера требует дополнительных ограничений в его аккаунте и сверки. В старой токеновой схеме резервирования нет: она не предназначена для нового внутреннего теста.

## Что видит администратор и сотрудник

Карточка пользователя показывает остаток USD, использованный лимит каждого окна, количество запросов, время сброса, срок доступа, суммарные входные/выходные токены, последние 30 расходов и последние 20 записей журнала. Неизвестные токены отображаются прочерком в расходе, а оценочная стоимость отмечена отдельно. Тексты запросов в биллинге не сохраняются. Список пользователей показывает денежный остаток и паузу; для деталей нужно открыть карточку.

Основной агент редактора получает персональный каталог и показывает бюджет API в строке состояния; наведение раскрывает окна и срок. Аккаунт с Bedrock видит фактически выбранную администратором модель. Отказы из-за бюджета и лимитов не должны запускать автоматические повторы. Старый установленный редактор продолжит ходить в тот же endpoint и будет ограничен сервером, но для корректного каталога и индикатора нужен обновлённый клиент. Отдельная панель `arni-agent` также показывает доступный бюджет и квоты запросов вместо прежнего дневного индикатора для таких аккаунтов.

## Запуск внутреннего теста

1. Проверить рабочий `ADMIN_PASS` в окружении сервера. Значение не нужно отправлять в чат. Встроенный пароль удалён: без настроенного пароля админка закрыта. Имя администратора сохраняет прежнее поведение: `ADMIN_USER`, если задан, иначе `admin`. Обновить каталог Bedrock штатным импортом и проверить актуальность цен/разрешений нужной модели.
2. Снять штатную резервную копию БД. Применить один раз `deploy/billing/20261014-budget.sql` к целевой БД: `prisma db execute --file deploy/billing/20261014-budget.sql --schema prisma/schema.prisma`. SQL добавляет таблицы и nullable-поля, сохраняет существующие балансы. В репозитории до этой работы не было истории Prisma migrations, поэтому этот файл — явное обновление существующей схемы. Повторное применение завершится ошибкой; не использовать `db push` или `--accept-data-loss` как замену на production.
3. Выпустить backend с новым Prisma Client (`prisma generate` выполняется в postinstall), затем обновлённый редактор/его встроенный Copilot. Применение схемы должно предшествовать новому backend, поскольку он читает бюджет и для старых пользователей.
4. Сотрудник входит своим аккаунтом. Администратор выбирает провайдера и разрешённую модель, затем выдаёт $20/30 дней в новой форме. Кнопка старого начисления токенов для этого теста не используется.
5. На одном тестовом сотруднике проверить реальный короткий запрос: правильная модель, запись usage, изменение остатка и сохранение времени сброса после перезапуска редактора. Затем выдать доступ остальным. Проверка реального API требует отдельного фактического вызова; локальные тесты её не заменяют.
6. В первый день смотреть `estimated`, `pending`, превышения расхода и доступность модели; по факту скорректировать $2/$5 и лимиты запросов.

Не откатывать старый backend на аккаунтах с действующими денежными бюджетами: он снова начнёт использовать прежний токеновый баланс. При проблеме безопаснее остановить выдачу/использование через бан участников и исправить сервер. Удаление новых таблиц уничтожит журнал и не является штатным откатом.

## Следующие этапы: купоны, рубли, подписка

Первый этап выдаёт персональный бюджет прямо из админки. Это выполняет задачу бесплатного доступа сотрудников; вводимых пользователем промокодов ещё нет. Если нужен самовыкуп кода, добавить `Coupon` и `CouponRedemption`: сумма, срок, число применений, привязка к аккаунту/организации, хеш кода и атомарное погашение с уникальным ключом начисления. Один общий публичный код без ограничений не использовать для оплачиваемого компанией API.

Для продажи за рубли добавить `PaymentOrder` (user, amountKopecks, currency=RUB, выбранный продукт, providerPaymentId, status) и события оплаты. Платёжный провайдер компании нужно уточнить; из голосового сообщения нельзя надёжно определить его название. Подписку открывает только проверенное серверное уведомление или сверка статуса у провайдера, а не переход на страницу «успех». Проверять подпись, сумму, валюту и идентификатор заказа. Начисление и отметку обработанного paymentId выполнять одной транзакцией. Повторы webhook должны быть без повторного начисления; возвраты и отмены требуют отдельного правила.

Для классической подписки добавить `Subscription`/`Entitlement`: начало/конец оплаченного периода, месячный включённый бюджет, правила переноса, возобновление/отмена и возвраты. Сначала можно продавать 30 дней доступа разовым платежом; автоматическое списание — отдельный следующий этап. Бесплатная выдача и платежи создают одинаковое право доступа, но имеют разные основания в журнале.

Розничная цена в RUB и $20 расходов API — разные цифры. Цену подписки выбирать после реального теста с учётом номинальной цены API после окончания грантов, платёжных комиссий, инфраструктуры и поддержки. Текущий код не задаёт курс RUB/USD, маржу или обещание фиксированного количества задач/токенов за подписку. Деньги клиента хранить в копейках; расход провайдера — в USD micro-units; утверждённый курс/бюджет продукта сохранять в заказе, а не менять задним числом.

## Проверки

`powershell -NoProfile -ExecutionPolicy Bypass -File scripts/test-billing.ps1` поднимает отдельную PostgreSQL 17 на случайном loopback-порту, применяет сохранённую старую схему `scripts/fixtures/billing-before.prisma`, сохраняет fixture старого баланса, применяет SQL-обновление и запускает `test-billing.cjs`. Рабочие `.env` не используются для соединения: URL процесса заменены на тестовые. После теста сервер останавливается и его проверенный временный каталог удаляется. В Windows sandbox для локальных процессов/соединений может потребоваться разрешённый запуск вне sandbox.

Проверены: миграция без потери баланса, конкурентные начисления и расходы, идемпотентность закрытия, 5h/weekly/requests/balance, независимый сброс окна, free, бан/пауза/срок, отсутствие usage, разделённый SSE, отмена клиента и route с подменёнными провайдерами. Отдельно проверены TypeScript/lint backend, целевые Vitest клиента и форма админки в браузере с чтением сохранённого состояния. Production deployment, собранный Windows installer и оплаченный live-вызов этим не подтверждены.

Расчёт опирается на официальные описания [usage OpenRouter](https://github.com/OpenRouterTeam/docs/blob/main/docs/api_reference/overview.mdx), [максимальной цены маршрута](https://github.com/OpenRouterTeam/docs/blob/main/docs/guides/routing/provider-selection.mdx) и [usage Converse Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference.html).
